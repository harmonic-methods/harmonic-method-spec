Start with the [Capability Beat and its Coda](/docs/getting-started/define-a-beat). A [Beat Version](/docs/method/primitives#beat-versions) describes the next increment toward that outcome. One or more Revisions deliver it.

## Plan the next increment

1. **Choose a bounded change.** Decide which part of the capability you can deliver and verify now.
2. **Write the plan.** Describe what is in scope, what is deferred, and how someone will verify the result. Use the [Beat Version Plan Quality check](/docs/method/quality#gates) to review the plan.
3. **Deliver and verify.** Link the Revisions to the Beat Version, check the result against the acceptance criteria, and record decisions as Notes on the Beat.

## Worked example

Start with showing approval status on the estimate record. Leave status notifications for a later increment. Verify that a recorded approval or decline by the designated approver changes the displayed state and that an estimate awaiting a decision remains pending.

## Start from existing work [#existing-work]

You can introduce the method while a capability is already being delivered or used:

1. Describe the capability and the Coda it serves using the current system as evidence. Keep the capability distinct from the tasks that first built it.
2. Capture the constraints and decisions that still matter. Confirm uncertain history with the people who can verify it instead of inventing rationale.
3. Assess the capability's Coda and its fit with related capabilities. Take a [Downbeat](/docs/method/cadence#downbeat) to preserve what is true now.
4. Plan the next bounded improvement. Create Beat Versions for future work; do not create retrospective plans to stand in for delivered history.

A Beat remains `open` while its capability matters, including after its first delivery. Teams may use additional workflow labels, but those labels do not replace the published lifecycle.
