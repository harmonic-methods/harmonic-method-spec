Run a quality check once you have a draft Coda. In this walkthrough, you'll check the estimate approval status Capability Beat and see what would make its promise clearer.

## Run the review

1. **Choose the rubric.** Use Coda Quality for a Coda with a parent, including the example Beat. Use Root Coda Quality for a Coda with no parent. See the [quality model](/docs/method/quality#gates) for the available checks.
2. **Gather the evidence.** For the Beat, bring its title, Coda, and description, plus the parent Coda, sibling Beats, and relevant Notes you have. For a root Coda, bring the statement and the Notes and other records that support its claims.
3. **Apply the rubric as written.** Work through it by hand or provide the rubric and those materials in your organization's approved AI workspace. If you have the starter kit, the [sample review instructions](/docs/getting-started#starter-kit) show how to supply files. If you do not have the full rubric, use the example below to practice reviewing the wording before scoring.
4. **Read the reasons and decide what to change.** Keep the rubric result with the spec set version and inputs used. Have the responsible person review the suggested improvements. Recheck the Coda after a material change.

## Worked example

Bring the Beat and its parent Coda from the earlier steps, along with the Note about the designated approver. Assess the title, Coda, and description together.

For **Clear**, the Coda's phrase “current approval state” is broad, but the description already defines pending, granted, and declined. Naming those states in the Coda could make the outcome easier to read on its own.

For **Substantial**, ask whether approval-status visibility is a meaningful capability in its own right or part of a broader approval capability. Compare sibling outcomes before deciding. If it belongs within a broader Beat, plan the visibility improvement as a Beat Version there. The walkthrough supplies no sibling list, so overlap and fit remain provisional.

## Save your output [#save-output]

### Work with documents — recommended [#save-documents]

Save the assessment beside the draft it reviewed, for example in `coda-review.md`. Include the rubric and spec set used, the inputs and missing context, the scores or findings, and the improvement you chose. Update the draft with approved changes and record the reasoning. Recheck it after a material change.

<details id="save-repository">
<summary>Save in a repository</summary>

Save the assessment as a Markdown review outside the validated entity tree, such as `reviews/estimate-approval.md`. This is a review document, not a new method entity.

Apply approved changes to the Coda or Beat files. Record material decisions in Notes, preserving earlier Coda statements and superseding published Notes when their meaning changes. Run the conformance checker, review the diff and new files, and commit through your team's normal workflow. A passing structural check does not replace the quality review.

[See validation and commit instructions](/docs/implementation/use-a-repository#validate).

</details>
